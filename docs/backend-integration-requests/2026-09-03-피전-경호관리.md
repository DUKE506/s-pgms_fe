## 요청 1 — 배치장소 4필드 확장

**API**: `AddDeployRequestDto` / `UpdateDeployRequestDto` / `GetDeployDetail` / `DEPLOY_REQUEST` 테이블

**문제**
- 쓰기 DTO와 DB(`DEPLOYMENT_PLACE`)는 배치장소가 **단일 문자열 1개**인데, 실제 배치요구서
  양식과 프론트 폼은 주거지/직장지/기타1/기타2 **4필드**.
- `GetDeployDetail` 응답에는 4필드(`guardHomeLoc` / `guardWorkLoc` / `guardEtcLoc1` /
  `guardEtcLoc2`)가 이미 있으나 전부 `null`로 내려옴 — 단일 컬럼(`deploymentPlace`)과
  4필드가 서로 다른 저장소로 보이고 생성 시 매핑이 안 걸림.
- 프론트는 현재 `deploymentPlace`에 **주거지 값만** 전송 중(직장지·기타 3개는 미전송).

**해결 요청안**
- `AddDeployRequestDto` / `UpdateDeployRequestDto`에 배치장소 4필드 추가, 생성·수정 시
  `guardHomeLoc` 등에 저장.
- `GetDeployDetail` 응답의 기존 4필드와 이름·의미를 일치시켜 왕복 보장.
- `DEPLOY_REQUEST`에 컬럼 3개 추가.
- 축소가 불가피하면 최소 주거지/직장지 2필드.

## 요청 2 — 경호건 근무 스케줄 조회 API 신설

**API**: 해당 엔드포인트 없음 (`GetDeployDetail` / `GetGuardCaseDetail` 응답에 스케줄 블록 없음)

**문제**
- 경찰 경호 상세의 "근무자 배정" 카드를 채울 데이터 소스가 실백엔드에 없음.
- 근무자 마스터 목록(`GET Guard/Stec/W/GetGuardList`)은 본사 전용이라 피전(경찰서) 계정이
  호출 불가 → 프론트에서 근무자 ID로 조인하던 방식이 실백엔드에서 동작 불가.
- 백엔드 확인(2026-09-02): "경호 상세에서 근무 스케줄을 조회하는 API를 누락했다".

**해결 요청안**
- `deployReqSeq`(또는 `caseSeq`) 기준으로 **일자별 근무 스케줄 + 각 근무자의 표시정보
  (이름/사번/연락처)를 embed**한 조회 엔드포인트 신설. 예:
  `GET Deploy/Police/W/GetCaseSchedule`, 또는 `GetGuardCaseDetail` 응답에 스케줄 블록 추가.
- 근무자 정보는 ID만 주지 말 것(피전은 근무자 마스터 접근 권한 없음).

## 요청 3 — 근무자별 보안서약·개인정보동의서 조회 API 신설

**API**: 해당 엔드포인트 없음 (`GetDeployDetail` 응답의 `docAgreeDetail`은 접수 단계 실측에서 항상 `[]`)

**문제**
- 경찰 경호 상세의 "보안서약 및 개인정보동의서" 카드는 **등록된 근무자별로** 서약서
  업로드 상태와 다운로드를 보여주는데, 이를 채울 데이터 소스가 실백엔드에 없음.
- 근무 스케줄(요청 2)과 성격이 다름 — 스케줄은 일자·근무조·시간, 이쪽은 근무자별
  파일(서약서/동의서) 메타. 한 응답에 섞기보다 별도 조회가 맞다고 판단.

**해결 요청안**
- `deployReqSeq`(또는 `caseSeq`) 기준으로 **근무자별 보안서약서·개인정보동의서 목록**
  (근무자 식별·표시정보 + 파일명 + 업로드 여부 + 다운로드 경로)을 돌려주는 조회
  엔드포인트 신설. 예: `GET Deploy/Police/W/GetCaseConsentDocs`.
- 파일 다운로드 방식(직접 URL / 별도 다운로드 엔드포인트)도 함께 정리.

## 요청 4 — 배치요구서 수정용 상세조회 API 신설

**API**: `GET Deploy/Police/W/GetDeployDetail` (현재 이걸로는 수정 prefill 불가)

**문제**
- `GetDeployDetail`은 배치요구서 상세조회지만, 응답이 피전 상세페이지에 표시되는
  **"기본정보" 형태**로 옴. 기본정보는 원래 본사 관리자가 배정 이후 등록하는 데이터이고,
  접수 단계에는 없으므로 배치요구서 내용을 기본정보 형태로 임시 매핑해 내려줌.
- 그 과정에서 배치요구서 원본 필드가 누락됨: 성별 `suspectGender`, 생년월일
  `suspectBirthDate`, 직업 `suspectJob`, 사건개요 `caseSummary`, 참고사항 `caseMemo`,
  배치장소 4필드(요청 1).
- 배치요구서 수정 화면은 신규접수와 같은 폼을 재사용 → 위 필드가 폼 필수값이라, 누락되면
  저장 불가. 빈 값을 `UpdateDeployRequest`에 실으면 400 또는 기존 DB 값을 덮어쓸 위험.
  → **수정 화면 착수 보류 중.**

**해결 요청안**
- `deployReqSeq` 기준으로 배치요구서에 제출된 **원본 값을 그대로** 돌려주는 GET 엔드포인트
  신설. 예: `GET Deploy/Police/W/GetDeployRequestForEdit`.
- 응답 스키마는 `UpdateDeployRequestDto`와 대칭 + `statusName`(배치기간 잠금 판정용) +
  `mgmtNo`.
- 배정 이후 상태에서 이 화면에 들어오는 경우의 소스도 함께 정리(`GetGuardCaseDetail`
  분기 여부).
