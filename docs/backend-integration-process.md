# 백엔드 연동 작업 프로세스

`docs/backend-integration-analysis.md`(스웨거/DB 갭 분석), `docs/backend-integration-issues.md`
(설계 변경 요청 목록)를 바탕으로 실제 연동 작업을 시작할 때 지킬 규칙입니다(2026-08-31
결정). 목적은 "mock과 실제 백엔드가 다를 때마다 매번 기준 없이 헤매지 않는 것" — 불일치의
심각도에 따라 세 갈래로 처리 방식을 나눕니다.

## 원칙 1 — 사소한 불일치는 제외하고 진행 + 기록

기능 전체를 막지 않는 수준의 불일치(예: 화면에 쓰던 필드 하나가 실제 API/DB에 없음, 혹은
의미가 살짝 다름)는:

1. 그 필드/기능만 스코프 아웃하고 나머지 연동 작업을 계속 진행한다 — **매번 사용자에게
   확인받지 않는다.**
2. `docs/backend-integration-exclusions.md`에 즉시 기록한다(형식은 그 문서 참고).
3. **"사소하다"의 판단 기준**: 그 필드/기능이 빠져도 화면의 핵심 흐름(작성→저장→조회)이
   깨지지 않고, 되돌릴 수 없는 정보 손실이 아닌 경우. 애매하면 사소한 쪽으로 임의
   판단하지 말고 원칙 3(트레이드오프)으로 넘긴다.

## 원칙 2 — 작업을 막는 수준의 불일치(블로커)

**1차 목표는 착수 전 분석 단계에서 미리 걸러내는 것** — 화면 단위로 연동을 시작하기 전에
관련 API/DB 구조를 먼저 대조해보고, 갭 분석 문서에 없는 새로운 블로커가 있는지 그때
확인한다.

그래도 작업 도중 사전에 못 거른 블로커를 만나면, 상황에 따라 둘 중 하나로 처리한다:

- **바로 물어봐도 되는 경우** (짧게 확인하면 바로 이어서 진행 가능한 질문): 대화 중 바로
  사용자에게 확인한다.
- **당장 답을 들을 수 없거나, 이 블로커와 무관한 다른 작업을 이어서 계속할 수 있는 경우**:
  `docs/backend-integration-blockers.md`에 기록해두고, 이 블로커와 무관한 다음 작업으로
  넘어간다. 형식은 그 문서 참고 — 상황/문제/해결 필요 사항/해결방안 후보를 반드시 포함.

## 원칙 3 — Mock/백엔드 설계가 트레이드오프 있게 다를 때는 임의로 정하지 않는다

예: 실제 DB 구조까지 바꿔야 끝나는 근본적인 차이 vs. API 한두 개만 얹으면 되는 가벼운 차이
— 둘 다 가능한 선택지가 있을 때는 그 자리에서 마음대로 하나를 골라 진행하지 않는다.

1. 선택지들과 각각의 트레이드오프(작업량, 리스크, 나중에 되돌리기 쉬운 정도 등)를 정리해서
   제시한다.
2. 사용자와 논의해서 결정한다.
3. 결정된 내용에 따라 진행하고, 결정 이유를 해당 화면/기능의 진행기록에 남긴다(기존
   `.claude/loop-screens/PROGRESS.md`의 iteration 로그와 같은 방식).

이건 원칙 1(사소한 것)과 원칙 2(블로커)의 중간 지대 — 진행이 아예 불가능한 건 아니지만
어느 쪽으로 가느냐에 따라 이후 작업량·설계가 크게 달라지는 경우에 해당한다.

## 문서 간 관계

| 문서 | 역할 | 갱신 시점 |
|---|---|---|
| `backend-integration-analysis.md` | 스웨거/DB 구조 자체의 갭 분석 | 큰 구조적 발견이 있을 때만 |
| `backend-integration-issues.md` | 백엔드/기획에 설계 변경을 요청할 사항 | 발견되는 대로 추가, 논의 후 상태 갱신 |
| `backend-integration-exclusions.md` | 실제 연동 작업 중 제외한 필드/기능 로그 (원칙 1) | 연동 작업 중 수시로 |
| `backend-integration-blockers.md` | 실제 연동 작업 중 만난 블로커 로그 (원칙 2) | 연동 작업 중 블로커 발생 시 |
| `backend-integration-responses/` | 스웨거에 없는 실제 응답 샘플 저장(엔드포인트 1개당 파일 1개) | 화면 착수 전, 그 화면이 쓰는 API 중 샘플 없는 게 있을 때 |
| 이 문서 | 위 문서들을 언제 어떻게 쓰는지에 대한 규칙 | 프로세스 자체가 바뀔 때만 |
