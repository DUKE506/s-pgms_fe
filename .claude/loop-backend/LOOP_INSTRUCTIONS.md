# LOOP_INSTRUCTIONS — 한 iteration 실행 절차

`TASK.md`의 정책·정지 조건을 항상 우선한다. 아래는 정상 경로.

한 iteration = 3국면(**①계획 → ②실행 → ③반영**) + 3게이트(**G1·G2·G3**).

```
0. 유형 판정
─────────────────────────────────── ① 계획
1. 다음 대상 확정
2. 작업계획서 (templates/PLAN.md)
                                     〔G1 승인 — 항상 멈춤〕
─────────────────────────────────── ② 실행
3. 프로브 (guides/PROBE.md)
4. 프로브 결과 제시 + 발견사항 분류
                                     〔G2 결정 게이트 — 조건부 멈춤〕
5. 구현
6. 검증
─────────────────────────────────── ③ 반영
7. 완료 보고 (templates/REPORT.md)
                                     〔G3 승인 — 항상 멈춤〕
8. 문서 갱신
9. 커밋
10. (섹션 마지막 행이면) 섹션 종료 → guides/SECTION_BOUNDARY.md
```

---

## 0. 유형 판정

`PROGRESS.md`를 읽고 이번 iteration이 어느 유형인지 정한다(`TASK.md` "iteration 단위와 유형").

| 유형 | 스킵되는 것 |
|---|---|
| 연동 | 없음 (전체) |
| 검증전용 | **5. 구현 스킵** — 3·4·6·7~10만. (테스트 1건 추가 정도는 함) |
| 회신반영 | **2. 계획서 축약**(무엇을 반영하는지 3줄), **3. 프로브 = 백엔드 변경분 확인** |

---

## ① 계획

### 1. 다음 대상 확정

- 대기 중인 백엔드 회신 완료분이 있으면 **그 반영(회신반영 iteration)을 먼저** 한다.
- 없으면 `PROGRESS.md` 표에서 `대기` 중 **번호가 가장 빠른 행**. 임의로 순서 안 바꿈.
- `docs/backend-integration/matrix.md`에서 그 화면이 호출하는 API를 전부 나열. "N번 이후
  재검증" 표시가 있으면 지금이 그 시점인지 확인.
- ⚠️(mock 전용) 항목은 `findings.md` 상태부터 확인.
- 스웨거(`docs/api-swagger.json`)가 갱신됐을 수 있으니 요청/응답 스펙 재확인.
- ID 체계(문자열 → 정수 seq), 상태값(한글 → 정수 코드) 변환 지점을 미리 식별.

### 2. 작업계획서

`templates/PLAN.md` 구조로 낸다. 프로브에서 결론이 갈릴 만한 항목은 "결정 필요"에
선택지로 적고, 임의로 정하지 않는다.

### 〔G1 승인 — 항상 멈춤〕

방향·범위 합의. 사용자의 명시적 승인("진행하자") 전까지 ②로 넘어가지 않는다.

---

## ② 실행

### 3. 프로브

`guides/PROBE.md` 참고. 계획서에서 나열한 API마다 `docs/backend-integration/responses/`에
실측 샘플이 있는지 확인하고, 없으면 `local/_probe-NN.sh`로 실백엔드에 직접 호출해 확보·
저장한다. 되돌리기 어렵거나 부작용 있는 호출(계정 생성, 비밀번호 변경 등)은 먼저 사용자에게
확인받는다.

### 4. 프로브 결과 제시 + 발견사항 분류

확보한 응답을 화면 단위로 요약해 제시한다 — 실제 필드 구조, mock과 다른 점, 예상 밖
값·누락. 발견사항을 두 갈래로 나눈다:

- **열린 결정** — 블로커 / 트레이드오프 / ⚠️mock전용 / 스웨거↔실제 불일치 / 계획서가
  "프로브 후 결정"으로 미뤄둔 항목
- **추후 처리** — 사소하거나(제외) 구현하면서 자연히 드러나는 것

### 〔G2 결정 게이트 — 조건부 멈춤〕

- **열린 결정이 1개라도 있으면 ★ 멈춤.** 전부 닫기 전엔 코드 한 줄도 안 쓴다(결정 안
  하고 구현 → 되돌리기 비용). 닫은 결정은 `PROGRESS.md` iteration 로그의 `결정:` 항목에
  선택지·고른 것·근거로 남긴다.
- **열린 결정이 0개면** "프로브 깨끗, 계획대로 구현" 한 줄 통보 + 사소한 건 `findings.md`
  (종류: 제외)에 적고 그대로 진행.

### 5. 구현 (검증전용이면 스킵)

- 해당 화면이 쓰는 `features/*/api/*.ts` 함수를 실 엔드포인트로 교체(`apiFetch` 래퍼 재사용
  — base path·인증 방식 자체가 바뀌면 `client.ts`부터).
- 응답 필드명이 mock과 다르면(camelCase ↔ snake_case 등) 그 API 파일 안에서 변환하고
  컴포넌트 타입/렌더링은 최대한 그대로.
- 상태값 매핑(정수 코드 ↔ 한글 라벨)은 공용 헬퍼로 뽑아 여러 화면이 재사용.
- **공유 코드 회귀 차단**: 다른 역할이 쓰는 mock 함수는 존치, role 분기로만 가른다.
- **테스트 더블**: `mocks/handlers/*`를 실 응답 shape로, `handlers` → `testOnlyHandlers`로
  이동(브라우저는 실백엔드로 프록시).

### 6. 검증

1. `npm run test` / `npm run lint` / `npm run build` 통과(ID·상태값 타입 바뀌면 테스트도 갱신).
2. 실백엔드 대상 `run-s-pgms` 드라이버(또는 브라우저)로 로그인 → 해당 화면 → 데이터가
   정상적으로 뜨는지, 액션이 실제로 반영되는지.
3. **회귀 확인** — loop-screens 때 승인받은 스크린샷과 레이아웃·데이터 표시 대조.
4. `console` 커맨드로 콘솔 에러 확인.
5. 4단계에서 "추후 처리"로 미룬 항목을 실물로 재판정 — 여전히 사소한지, 더 큰 문제였는지.

---

## ③ 반영

### 7. 완료 보고

`templates/REPORT.md` 형식으로, 무엇을 연동했는지 + G2에서 발견/결정한 것 + 6단계에서
처리한 결과를 종합해 제시한다.

### 〔G3 승인 — 항상 멈춤〕

명시적 승인 전까지 커밋하지 않는다. 수정 요청이 오면 6단계(검증)부터 다시 → 다시 제시.

### 8. 문서 갱신

| 문서 | 갱신 내용 |
|---|---|
| `PROGRESS.md` | 해당 행 상태·커밋 해시, iteration 로그(무엇을 했나 + `결정:` + 검증 결과) |
| `docs/backend-integration/matrix.md` | 해당 행 연동 완료 표시 |
| `docs/roadmap.md` | 백엔드 연동 Phase 체크박스 |
| `docs/backend-integration/findings.md` | 이번에 새로 적은 요청/제외/블로커 누락 없이 반영, 상태 갱신 |
| `CARRYOVER.md` | 이번에 생긴 재검증·데이터 대기 항목 추가 |

### 9. 커밋

**iteration당 커밋 2개**(커밋 전 항상 사용자에게 확인):
1. `구현/테스트` — `src/` 변경
2. `문서` — `PROGRESS.md`(커밋 해시 포함) + 나머지 문서

검증전용이면 문서 커밋 1개(+테스트 커밋). 해시 기록을 위한 별도 3번째 커밋은 만들지 않는다
— 1번 커밋 후 해시를 `PROGRESS.md`에 채워 2번 커밋에 포함.

### 10. 섹션 마지막 행이면

`guides/SECTION_BOUNDARY.md` 절차로 이번 섹션의 `findings.md` 누적분을 요청서로 묶어
전달한다. 응답은 기다리지 않고 다음 섹션으로.
