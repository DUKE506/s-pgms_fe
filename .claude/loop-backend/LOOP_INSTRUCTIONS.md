# Loop 절차 — 화면 1개 백엔드 연동

`TASK.md`의 정지 조건을 항상 우선한다. 아래는 정지 조건에 걸리지 않는 정상 경로.

## 1. 다음 대상 + API 목록 확정

- `PROGRESS.md`를 읽고 현재 상태 확인(진행 중인 항목이 있으면 그것부터)
- 없으면 `PROGRESS.md` 표에서 상태가 `대기`인 것 중 **번호가 가장 빠른 행**을 다음
  대상으로 고른다 — 이 표는 이미 "역할 단위로 완결 → 그 안에서 의존성 순서"로
  정렬돼 있으므로(피전 전체 → 운영/시스템관리자 전체 → 본부관리자 → 본청/지역청)
  임의로 순서를 바꾸거나 다른 역할 화면을 먼저 하지 않는다(`TASK.md` "Loop 단위" 참고)
- 상세 API 목록은 `docs/backend-integration-screen-api-matrix.md`에서 같은 화면을 찾아
  확인. "N번 이후 재검증" 표시가 있는 화면이면 지금이 그 재검증 시점인지 확인
- 그 화면이 호출하는 API 전부를 매트릭스에서 나열 — ⚠️ 표시(mock 전용)가 있으면
  `docs/backend-integration-issues.md` 상태부터 확인
- 실제 엔드포인트의 요청/응답 스펙이 이 시점 기준으로도 분석 문서와 일치하는지 확인
  (스웨거가 갱신됐을 수 있음 — `docs/api-swagger.json` 재확인)
- ID 체계(문자열 → 정수 seq), 상태값(한글 문자열 → 정수 코드) 변환이 필요한 지점을
  미리 식별해둔다

## 2. 응답 사전 테스트 + 결과 제시

- 스웨거엔 Response 스키마가 없으므로(`analysis.md` 4-1), 1번에서 나열한 API마다
  `docs/backend-integration-responses/`에 실제 응답 샘플 파일이 있는지 확인한다.
  없으면 사용자에게 스웨거 UI에서 직접 테스트해서 저장해달라고 요청한다(형식은 그
  폴더의 `README.md` 참고)
- 확보된 응답들을 화면 단위로 요약해서 사용자에게 제시한다 — 실제 필드 구조, mock과
  다른 점, 예상 밖 값/누락 등
- 여기서 발견되는 문제를 바로 두 갈래로 나눈다:
  - **즉시 처리 필요** — 지금 결정하지 않으면 구현 방향 자체가 틀어지는 것(블로커/
    트레이드오프, `process.md` 원칙 2·3) → 이 자리에서 바로 사용자와 확인/결정한다
  - **추후 처리 가능** — 사소하거나(원칙 1) 구현하면서 자연스럽게 드러나는 것 →
    표시만 해두고 3번(구현)으로 넘어간다

## 3. 구현

- 2번에서 결정된 내용을 반영해서, 해당 화면이 쓰는 `features/*/api/*.ts` 함수들을
  실제 엔드포인트로 교체한다(`apiFetch` 래퍼는 그대로 재사용 — base path나 인증
  방식 자체가 바뀌면 `client.ts`부터 먼저 손댄다)
- 응답 필드명이 mock과 다르면(camelCase ↔ snake_case 등) 그 API 파일 안에서 변환하고,
  컴포넌트 쪽 타입/렌더링은 최대한 그대로 둔다
- 상태값 매핑(정수 코드 ↔ 한글 라벨)은 공용 헬퍼로 뽑아서 여러 화면이 재사용하게 한다

## 4. 검증

1. `npm run test`, `npm run lint`, `npm run build` 모두 통과 확인(ID·상태값 타입이
   바뀌면 관련 테스트도 함께 갱신)
2. 실제 백엔드를 대상으로 `run-s-pgms` 드라이버 또는 브라우저로 로그인 → 해당 화면까지
   이동 → 데이터가 정상적으로 뜨는지, 액션이 실제로 반영되는지 확인
3. **회귀 확인** — loop-screens 때 승인받은 스크린샷과 비교해 레이아웃·데이터 표시가
   달라지지 않았는지 확인한다(달라졌다면 API 응답 구조 차이 때문일 가능성이 큼)
4. `console` 커맨드로 콘솔 에러 없는지 확인
5. 2번에서 "추후 처리"로 미뤄둔 항목들을 여기서 실물로 재확인한다 — 여전히 사소한지,
   사실은 더 큰 문제였는지 재판정

## 5. 마무리 정리

- 검증 중 새로 나온 문제 + "추후 처리" 항목들의 최종 처리 상태를 확정한다(수정 완료 /
  `exclusions.md` 기록 / `blockers.md` 기록)

## 6. 제시 + 승인 대기 (★ 여기서 반드시 멈춤)

- 무엇을 연동했는지, 2번에서 발견한 사항, 5번에서 처리한 결과를 종합해서 제시한다
- **사용자의 명시적 승인 전까지는 다음 단계로 진행하지 않는다**
- 수정 요청이 오면: 반영 → 4번(검증)부터 다시 → 다시 제시

## 7. 승인 후 마무리

- `docs/backend-integration-screen-api-matrix.md`의 해당 행에 완료 표시
- `docs/roadmap.md`의 백엔드 연동 Phase 체크박스 갱신
- `PROGRESS.md` 갱신(완료로 표시, 커밋 해시 기록)
- 이번 iteration에서 `exclusions.md`/`blockers.md`/`issues.md`에 새로 적은 내용이 있으면
  누락 없이 반영됐는지 재확인
- 커밋(구현 커밋 + 문서 체크 커밋, 커밋 전 항상 사용자에게 확인 — 지금까지 해온 방식대로
  분리하거나 사용자가 원하면 합침)
- 다음 iteration으로 — 단, 자동으로 이어서 진행하지 않고 사용자가 "다음 화면"이라고
  말하면 1번부터 다시 시작
