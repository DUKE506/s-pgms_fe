# 작업계획 템플릿 (loop-backend 화면 단위)

사용자가 "#NN 작업계획 정리해줘"라고 하면 이 구조로 낸다. `LOOP_INSTRUCTIONS.md`가
실행 절차라면, 이 문서는 **착수 전에 사용자와 공유하는 계획서의 형태**다.

읽는 사람이 코드를 안 보고도 "무엇을 / 어디를 / 왜 / 어떻게 검증"이 바로 잡히게 쓴다.

## 작성 규칙 (5개)

1. **표 셀엔 짧은 값만.** 설명은 표 밖 문장으로, 한 문단 3~4줄 이내.
2. **중첩 불릿 최대 2단계.** 3단계 이상 들어가면 문장으로 풀거나 표로 바꾼다.
3. **결론 먼저.** 프로브·조사 결과는 "핵심: …" 한 줄을 맨 앞에 두고 세부는 그 뒤.
4. **코드 식별자는 첫 등장 때 `(무엇을 하는지)`를 즉시 붙인다** — 함수·필드·변수뿐
   아니라 **API명도 예외 없음**. 예: `GetHistoryList`(끝난 경호건 목록을 주는 API),
   `listPoliceStationHistory`(경찰서 이력 목록을 가져오는 새 함수).
5. **구현 범위에선 응답 필드를 전부 훑는다.** 화면에서 안 쓰는 필드는
   "미사용(이유)"라고 명시 — 조용히 빼지 않는다.

## 섹션 구조

### 1. 개요

- 첫 문장: **이번 #NN이 어떤 역할의 어떤 화면이고, 무슨 기능이 있는지**(목록 조회 /
  생성 / 수정 / 상세 등)를 한글로 풀어서. 읽는 사람이 화면을 다시 떠올리게.
- 주의할 구조가 있으면 짧게(예: 이 컴포넌트를 다른 역할이 공유함 → 이번엔 일부만 전환).
- 그다음 작은 표: 대상 경로 / 섹션·섹션경계 여부 / 선행 조건(데이터·의존).

### 2. 프로브 요약  (읽기 전용 실측을 돌린 경우만)

- "핵심: …" 한 줄.
- 표: `확인한 API` / `기대한 결과` / `실제 · 문제점`. 셀은 한 줄, 길면 표 아래 각주.
- 응답 필드 구조에서 mock과 다른 점, 예상 밖 값·누락을 여기 적는다.

### 3. 결정 필요  (없으면 "없음" 한 줄)

- 진행 방향이 갈리는 항목만. 선택지 + 각 트레이드오프. 임의로 정하지 않는다.
- 사소해서 그냥 제외할 것들은 여기 말고 "→ exclusions로 처리" 한 줄로.

### 4. 구현 범위

- 기능별로 문단 하나씩(목록 조회 / 상세 조회 / …). 각 문단은:
  - 새로 만드는 함수 `(설명)` → 호출하는 API `(설명)` → 파라미터 `(설명)`
  - 응답 → 화면 필드 매핑을 문장으로. 규칙 5(전 필드 훑기) 적용.
- 마지막에 **공유 코드 회귀 차단**을 한 문단(기존 mock 함수 존치 / role 분기 등).
- **테스트 더블**에 뭘 추가하는지 한 줄.

### 5. 검증 계획

- 체크리스트(불릿, 각 1줄): `npm run test`/`lint`/`build` / 실백엔드 `run-s-pgms`로
  어떤 계정으로 어디까지 / 회귀(승인된 화면 무변경) / 콘솔 에러.

### 6. 마무리

- **문서 갱신**: matrix 해당 행 / roadmap / PROGRESS #NN.
- **이월**: 다음 화면·섹션으로 넘기는 것(재검증 예정 / issues 후보).
- **커밋**: 분할 여부(기본 구현/문서 2분할).

### 예상 결과

- 1~2줄. 완료 / 부분완료(△) 여부와 이유, 재검증 이월, 다음 대상.
