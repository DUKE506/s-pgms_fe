# Loop: 백엔드 API 연동 (화면 단위)

## 목표

`docs/backend-integration-screen-api-matrix.md`에 정리된 역할×화면×API 목록을 하나씩
실제 백엔드 연동으로 바꾼다. 화면 자체(UI)는 이미 구현·승인된 상태이므로, 이 loop는
"mock API 호출 → 실제 API 호출"로 데이터 계층만 교체하는 작업이다.

## 왜 별도 loop인지 (loop-screens와 다른 점)

`loop-screens`(화면 신규 구현)와 표면적으로는 비슷해 보이지만 완료 기준이 다르다:

- loop-screens: 목업 대비 스크린샷 승인이 완료 기준
- loop-backend: 화면은 이미 승인됐고, "실제 API 호출로 정상 교체 + 기존 승인 화면 대비
  회귀 없음"이 완료 기준

또한 매 iteration마다 참고해야 하는 문서 세트가 다르다(아래 정지 조건 참고) — 두 종류의
작업을 한 절차에 섞으면 절차 문서 자체가 지저분해진다고 판단해 분리했다(2026-09-01 결정,
`docs/backend-integration-process.md` 참고).

## Loop 단위

`.claude/loop-backend/PROGRESS.md`의 표 한 행 = 1회 iteration. **개발(연동)은 화면
단위**다 — 한 섹션이 끝날 때까지 다른 화면을 안 건드린다는 뜻이 아니라, 표를 한 행씩
순서대로 진행한다는 뜻.

**큰 틀(2026-09-03 재정렬)**: 경호건 생명주기(**메인 워크플로우**)를 앞으로 당기고,
그 검증까지 끝난 뒤 이력 → 게스트로 간다. 이전(2026-09-01)엔 계정권한 단위로 화면군을
통째로 끝내는 순서였는데, 배정 이후 상태를 *만들어내는* 화면(본사 배정·경호계획)이
뒤에 있어 앞쪽 피전 화면이 계속 "배정 후 미검증 → 재검증 이월"로 밀렸다. 그룹 순서는
A(피전 경호관리) → B(본사 메인 워크플로우 + 검증) → C(이력) → D(게스트).

그룹 **안에서는** 조회(읽기) API를 먼저 연결해야 뒤이어 연결하는 생성/수정 API의
결과를 실제로 확인할 수 있다. 그래서 PROGRESS.md 표는 "그룹 → 그룹 안에서의 의존성
순서"로 정렬돼 있다(근거는 `docs/backend-integration-screen-api-matrix.md`의 "권장
진행 순서"). "다음 대상"은 항상 PROGRESS.md에서 상태가 `대기`인 것 중 번호가 가장
빠른 행이다 — 임의로 순서를 바꾸지 않는다.

배정 이후 상태처럼 뒤 그룹이 데이터를 만들어야만 실존하는 경우(예: 경찰 쪽 경호
상세의 연장/단축요청은 본사가 배정해야 재현 가능), 매트릭스에 "N번 이후 재검증"이라고
표시된 화면은 그 시점에 다시 열어 확인한다(새 iteration이 아니라 기존 iteration의
후속 확인 — PROGRESS.md에 별도 행을 만들지 않고 비고에만 남긴다).

### 백엔드 요청은 섹션 단위 (2026-09-03)

**개발은 화면 단위지만, 백엔드에 설계 변경/누락 API를 요청하는 단위는 섹션이다.**
섹션 = 한 역할의 한 기능 영역(예: 피전 경호관리 = 경호목록·신규접수·상세·수정·접수취소).
대체로 위 그룹 경계와 일치한다(그룹 B는 본사 운영관리자 경호관리 전체가 한 섹션,
그룹 C 이력도 한 섹션).

- 한 섹션의 화면들을 iteration으로 훑는 동안 `issues.md`(설계 변경 요청)·`exclusions.md`에
  쌓인 항목을, **섹션이 끝나는 시점에 한 번에 묶어** 백엔드로 전달한다. 화면마다
  찔끔찔끔 요청하지 않는다.
- 요청 후 **응답을 기다리지 않고** 다음 섹션 작업을 계속한다(비블로킹).
- 백엔드가 요청분을 완료하면, **지금 붙잡은 화면은 마무리까지 하고**, 다음 화면 착수
  전에 백엔드 변경분 확인 → 코드 수정 → 반영 → 검증을 끼워 넣은 뒤 다음으로 넘어간다.
- `exclusions.md` 항목 중 "데이터 없어 재검증 예정"인 것은 백엔드 요청이 아니라 위
  "N번 이후 재검증"으로 처리되는 것이니 섞지 않는다.

상세 절차는 `docs/backend-integration-process.md` 원칙 4, `LOOP_INSTRUCTIONS.md`
1·7단계 참고.

## 정지 조건 (반드시 멈추고 사용자에게 물어볼 것)

`docs/backend-integration-process.md`의 3원칙을 이 loop에 그대로 적용한다:

- **사소한 불일치(원칙 1)**: 화면 전체 흐름을 막지 않는 필드/기능 하나가 빠지는 정도면
  묻지 않고 제외한 채 진행한다 — 대신 `docs/backend-integration-exclusions.md`에
  즉시 기록한다.
- **블로커(원칙 2)**: 진행 자체를 막는 불일치를 만나면, 간단히 확인 가능한 질문은 그
  자리에서 바로 사용자에게 묻는다. 당장 답을 듣기 어렵거나 이 블로커와 무관한 다른
  iteration을 이어서 진행할 수 있으면 `docs/backend-integration-blockers.md`에 기록하고
  다음 대상으로 넘어간다.
- **트레이드오프(원칙 3)**: mock/실제 설계 중 어느 쪽을 따를지에 따라 이후 작업량·설계가
  크게 달라지는 경우, 임의로 정하지 말고 선택지와 트레이드오프를 정리해 사용자와 논의한
  뒤 결정한다.
- 매트릭스에 **⚠️로 표시된 "mock 전용"(실제 API 없음) 항목**을 만나면 반드시
  `docs/backend-integration-issues.md`에 이미 기록돼 있는지 먼저 확인한다 — 없으면 신규
  이슈로 추가하고, 상태가 🔴(검토 전)면 처리 방향을 사용자와 먼저 정한다.
- 사용자의 명시적 승인 없이 다음 iteration으로 넘어가지 않는다(loop-screens와 동일 —
  ScheduleWakeup 기반 무인 자동진행 아님).
