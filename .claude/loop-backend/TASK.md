# TASK — 백엔드 연동 loop 정책·판단 기준

잘 안 바뀌는 것들. "지금 B가 B-1/B-2로 쪼개져 있다" 같은 **현재 상태**는 여기 말고
`PROGRESS.md`에.

## 목표

`docs/backend-integration/matrix.md`의 역할×화면×API를 하나씩 실제 백엔드 연동으로
바꾼다. 화면(UI)은 이미 `loop-screens`에서 구현·승인됐으므로, 이 loop은 데이터 계층만
`mock API 호출 → 실 API 호출`로 교체한다.

### loop-screens와 분리한 이유 (2026-09-01 결정)

- loop-screens 완료 기준 = 목업 대비 스크린샷 승인
- **loop-backend 완료 기준 = 실 API 호출로 정상 교체 + 기존 승인 화면 대비 회귀 없음**

참고 문서 세트도 다르고(아래 인덱스), 두 작업을 한 절차에 섞으면 절차 문서가 지저분해진다.

## iteration 단위와 유형

**1 iteration = `PROGRESS.md` 표 한 행.** 표를 한 행씩 순서대로 진행한다.

| 유형 | 무엇 | 밟는 국면 (`LOOP_INSTRUCTIONS.md`) |
|---|---|---|
| **연동** | mock 함수를 실 엔드포인트로 교체 | 전체 (①계획 → ②실행 → ③반영) |
| **검증전용** | 코드 변경 없이 실 API 동작·스코프만 확인 (예: 다른 역할이 같은 화면·API 재사용) | ②의 구현 스킵 — 프로브·검증·보고만. 결과물 = 문서 (+선택 테스트) |
| **회신반영** | 백엔드가 이전 섹션 요청분을 완료 통보 | ①계획 축약, ②프로브 = 변경분 확인 → 반영 → 검증 |

유형은 착수 시(`LOOP_INSTRUCTIONS` 0단계) 판정한다.

## 진행 순서 원칙

**그룹 순서: A(피전 경호관리) → B(본사 메인 워크플로우 + 검증) → C(이력) → D(게스트).**
경호건 생명주기(메인 워크플로우)를 앞으로 당긴다 — 배정 이후 상태를 *만들어내는* 화면
(본사 배정·경호계획)이 뒤에 있으면 앞쪽 피전 화면이 계속 "배정 후 미검증 → 재검증
이월"로 밀리기 때문(2026-09-03 재정렬).

**그룹 안에서는 조회(읽기) API를 먼저** 연결한다 — 그래야 뒤이어 붙이는 생성/수정 API의
결과를 실제로 확인할 수 있다. `PROGRESS.md` 표는 이 원칙대로("그룹 → 그룹 안 의존성
순서") 정렬돼 있다. **"다음 대상"은 항상 표에서 `대기` 중 번호가 가장 빠른 행** — 임의로
순서를 바꾸거나 뒤 그룹을 먼저 하지 않는다. 단, 대기 중인 백엔드 회신 완료분이 있으면
그 반영(회신반영 iteration)을 먼저 한다.

배정 이후 상태처럼 뒤 그룹이 데이터를 만들어야 실존하는 경우, 매트릭스에 "N번 이후
재검증"으로 표시하고 그 시점에 다시 연다(새 iteration 아님 — `CARRYOVER.md`로 추적,
`PROGRESS.md` 비고에 남김).

## 개발은 화면 단위 / 백엔드 요청은 섹션 단위

**섹션 = 한 역할의 한 기능 영역**(대체로 그룹 경계와 일치). 화면들을 iteration으로 훑는
동안 `docs/backend-integration/findings.md`에 쌓인 항목(설계 변경 요청)을, **섹션이 끝나는
시점에 한 번에 묶어** 백엔드로 전달한다(화면마다 찔끔찔끔 아님). 전달 후 응답은 기다리지
않고 다음 섹션 진행. 완료 통보가 오면 다음 화면 착수 전에 회신반영 iteration을 끼워
넣는다. 섹션 종료 절차는 `guides/SECTION_BOUNDARY.md`.

## mock ↔ 실제 간극 판단 3원칙

연동 중 mock과 실 API/DB가 어긋나는 걸 만나면:

1. **사소한 불일치** — 화면 전체 흐름을 막지 않는 필드/기능 하나가 빠지는 정도면 묻지
   않고 제외하고 진행한다. 대신 `findings.md`에 즉시 기록(종류: 제외).
2. **블로커** — 진행 자체를 막는 불일치. 간단히 확인 가능한 질문이면 그 자리에서 바로
   사용자에게 묻는다. 당장 답 듣기 어렵거나 무관한 다른 iteration을 이어갈 수 있으면
   `findings.md`에 기록(종류: 블로커)하고 다음 대상으로.
3. **트레이드오프** — mock/실제 중 어느 쪽을 따르냐에 따라 이후 작업량·설계가 크게
   달라지면, 임의로 정하지 말고 선택지와 트레이드오프를 정리해 사용자와 논의한 뒤 결정.

## 정지 조건 (게이트)

한 iteration에는 승인 게이트가 3개 있다(`LOOP_INSTRUCTIONS.md` 참고):

| 게이트 | 위치 | 성격 |
|---|---|---|
| **G1** | 계획 후 / 실행 전 | 항상 멈춤 — 방향·범위 합의 |
| **G2** | 프로브 후 / 구현 전 | **조건부 멈춤** — 열린 결정(블로커·트레이드오프·⚠️mock전용·스웨거↔실제 불일치·계획서가 미뤄둔 항목)이 있으면 전부 닫기 전엔 코드 한 줄도 안 씀. 0개면 기록만 하고 통과 |
| **G3** | 보고 후 / 커밋 전 | 항상 멈춤 — 결과 확인 |

그 외:
- ⚠️로 표시된 "mock 전용"(실 API 없음) 항목을 만나면 `findings.md`에 이미 있는지 먼저
  확인 — 없으면 신규로 추가, 상태가 🔴(검토 전)면 처리 방향을 사용자와 먼저 정한다.
- 사용자의 명시적 승인 없이 다음 iteration으로 넘어가지 않는다(ScheduleWakeup 기반 무인
  자동진행 아님). "다음 화면"이라고 말하면 `LOOP_INSTRUCTIONS` 0단계부터 다시 시작.
